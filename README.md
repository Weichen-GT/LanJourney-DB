# LanJourney-DB

Everything about the LanJourney PostgreSQL database (Supabase in prod, Docker locally).

| Path | What it is |
|---|---|
| [`build.sql`](build.sql) | **New database in one command**: runs `schema.sql` and every seed file in order (psql). Refuses to run on a database that already has tables. |
| [`schema.sql`](schema.sql) | **The schema** -- the single source of truth: tables, indexes, triggers, Row Level Security, the vocabulary-size tiers. Every past migration is already in it. Safe to re-run. |
| [`SCHEMA.md`](SCHEMA.md) | Readable reference of every table, column, key and index (generated from `schema.sql`). |
| [`reset.sql`](reset.sql) | **Wipe and rebuild**: drops every table, then recreates the empty schema (generated from `schema.sql`). |
| [`seed/`](seed) | **The vocabulary**, loaded in numeric order after the schema (`01`-`04` generated by LanJourney-lib, `05` folded in from two applied fixes). |
| [`migrations/`](migrations) | **Only changes prod still needs.** Hand-run (there is no migration runner; the backend uses `ddl-auto=validate`), each with verify queries. Once a file has run on prod, move it to `archive/migrations/`. |
| [`archive/`](archive) | Scripts already applied to prod, kept for the record. **Never run them**: `schema.sql` and `seed/` already contain their result. `archive/migrations/` = schema changes up to 2026-11-18; `archive/updates/` = one-time data fixes on prod (vocabulary fixes, the 2026-11-14 quiz-history delete). Older docs in the other repos still point at `migrations/<file>` or `updates/<file>`: the same file is under `archive/`. |
| `tools/` | `build_reset.py`, `gen_schema_doc.py` (below); `test_migration.sh` (tries a migration on throwaway databases: the `main` schema, a prod-like copy, and the current schema, plus re-runs); `verify_database.sql` (read-only checks); `spike_db.sh` (throwaway local database for the article-generation spike); report queries (`ai_cost_report.sql`, `conversation_monitoring.sql`, `generation_pilot.sql`, `new_word_review.sql`, `article_word_check.sql`). |

## Build a new database

Any new database (another environment, a fresh local one, a rebuilt project) -- create it empty, then:

```bash
psql "$DATABASE_URL" -f build.sql
```

It ends by printing the word and meaning counts (expect 11067, 21792, 20967). The seed files are too large for
the Supabase SQL editor; use `psql`. On Windows, run it from Git Bash or set `PGCLIENTENCODING=UTF8`.

To wipe an existing non-prod database first: `psql "$DATABASE_URL" -f reset.sql`, then load `seed/01` to `seed/05`
in order (or drop and recreate the database and run `build.sql`). **Never run `reset.sql` on prod** -- it deletes
every user and all progress.

Local Docker (from the LanJourney2.0 repo): `docker compose down -v && docker compose up -d` loads `schema.sql`
and the seed files listed in its `docker-compose.yml`.

## When you change things

- **Changed the schema:** edit `schema.sql`, then `python tools/build_reset.py` and
  `python tools/gen_schema_doc.py` (needs the PostgreSQL binaries; it uses a throwaway local server), and commit the
  three files together. For prod, also add a hand-run script to `migrations/` (test it with
  `tools/test_migration.sh`), and make sure it ends in the same schema as `schema.sql` -- including Row Level
  Security on a new table. After the owner runs it on prod, `git mv` it to `archive/migrations/`.
- **Changed the vocabulary:** regenerate the seed files with the LanJourney-lib pipeline (its README). For prod,
  add an in-place script (in `migrations/`, marked as a data fix) -- never reload meanings once real users exist
  (it cascades to their progress). After it has run on prod, fold it into a seed file so `build.sql` still gives
  prod's vocabulary, and archive the original.
